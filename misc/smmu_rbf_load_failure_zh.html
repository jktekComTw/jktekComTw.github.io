為什麼 SDM 無法把 RBF 載入 FPGA 的組態 SRAM

SMMU 位址轉譯不一致造成 timeout waiting for svc layer buffers 的完整分析

DE25-Standard Agilex 5 (A5ED013BB32AE4SCS) Linux 6.12.11 arm-smmu-v3 stratix10-svc of_fpga_region

0. 一句話結論

Bitstream 的資料本身一直放在正確的位置；出錯的是 傳給 SDM 的那個「位址數字」。 因為 stratix10-svc 掛在 SMMU 後面，驅動程式拿到的是 IOVA（裝置虛擬位址）， 但 SDM 不在 SMMU 後面，它把這個數字當成實體位址（PA）去讀 DRAM， 於是讀到完全不相干的記憶體，找不到 bitstream，也就永遠不回應 — 驅動程式因此卡在等待，最後逾時。

觀察到的錯誤訊息： 
[  698.226136] fpga_manager fpga0: writing new40kHz4.core.rbf to Stratix10 SOC FPGA Manager
[  705.512932] Stratix10 SoC FPGA manager firmware:svc:fpga-mgr: timeout waiting for svc layer buffers
同時 /sys/class/fpga_manager/fpga0/state 卡在 write， 寫入的行程進入不可中斷睡眠（D state，連 kill -9 都無效）。

1. 三種位址空間：VA、PA、DMA address

要理解這個問題，必須先分清楚三種位址。很多人把它們混為一談， 但它們是三個不同的東西：

位址型別 誰在使用 由誰產生 / 轉譯
VA
virtual address		 CPU、kernel 程式碼
（void * 指標）		 由 CPU 內的 MMU 轉譯成 PA
PA
phys_addr_t		 真實的 DRAM 位置 —（這就是實體位置本身）
DMA address
dma_addr_t / IOVA		 裝置發出匯流排交易時使用 由 dma_alloc_coherent() 等 DMA API 回傳； 若裝置在 IOMMU 後面則由 SMMU 轉譯
關鍵觀念： dma_addr_t 回答的問題是 「裝置要在匯流排上放哪個數字才能存取這塊緩衝區？」， 這和「這塊緩衝區在 DRAM 的哪裡？」是兩個不同的問題。 兩者不保證相等。

什麼情況下 dma_addr_t == PA？

情境 結果
裝置在會轉譯的 IOMMU 後面 dma_addr_t = IOVA ≠ PA ← 本板目前狀況
裝置沒有 IOMMU 對應（走 dma-direct） dma_addr_t == PA
IOMMU 設為 identity / passthrough domain dma_addr_t == PA
平台宣告了 dma-ranges 位移 dma_addr_t = PA − offset ≠ PA（需另外確認）

2. MMU 與 SMMU 的差別

兩者都是位址轉譯器，差別在於替誰轉譯。

MMU SMMU（ARM 對 IOMMU 的稱法）
位於 CPU 核心內部 匯流排上的獨立區塊
為誰轉譯 軟體 — 行程、kernel 做 DMA 的裝置
輸入位址 VA（虛擬位址） IOVA（裝置虛擬位址）
輸出 PA PA
分頁表粒度 每個行程一份 每個裝置（或每個 IOMMU group）一份
防護對象 行程之間不能亂讀彼此記憶體 裝置不能亂寫不該碰的記憶體

本板開機時 SMMU 的分組

arm-smmu-v3 16000000.iommu: ias 48-bit, oas 48-bit (features 0x001c1fef)
socfpga-dwmac 10810000.ethernet: Adding to iommu group 0
dwc2 10b00000.usb:               Adding to iommu group 1
sdhci-cdns 10808000.mmc0:        Adding to iommu group 2
stratix10-svc firmware:svc:      Adding to iommu group 3   ← 問題所在
dw_axi_dmac_platform 10db0000.dma-controller: Adding to iommu group 4
dw_axi_dmac_platform 10dc0000.dma-controller: Adding to iommu group 5
iommus 只管「裝置主動發起」的存取。 方向很重要：
方向由誰轉譯受 iommus 影響？
CPU → 裝置暫存器（MMIO / ioremap）CPU 的 MMU否
裝置 → 記憶體（DMA / bus-master）SMMU是

3. 三個當事人：只有兩個講同一種位址語言

當事人 看得懂的位址 在 SMMU 後面嗎？
CPU / 驅動程式 VA，並向 DMA API 取得 dma_addr_t —
stratix10-svc
（Linux 眼中的「裝置」）		 IOVA — 因為它有 iommus 屬性 是，iommu group 3
SDM
Secure Device Manager		 只認實體位址（PA） 不是 — 它根本不是 Linux 裝置

名詞澄清

  • SDM（Secure Device Manager）：FPGA 內部一顆獨立的硬化微處理器， 不屬於 fabric 也不屬於 HPS。它掌管整顆晶片的組態與安全 — 所有 bitstream（JTAG、QSPI、Avalon-ST、HPS mailbox）都要經過它， HPS 何時解除 reset 也由它決定。
  • SVC（service layer）：Linux 端與 SDM 溝通的服務層驅動， 即 stratix10-svc（compatible = "intel,agilex5-svc"）。 它位於 device tree 的 /firmware/svc（注意是 /firmware 而非 /soc， 因為它是軟體服務，不是記憶體映射週邊）。底下掛了三個服務： fpga-mgr（FPGA 組態）、fcs-hal（加密服務）、hwmon（電壓溫度）。
  • CRAM：FPGA 的組態 SRAM，存放 fabric 的實際配置。由 SDM 寫入。

完整呼叫鏈

of_fpga_region → fpga-mgr → stratix10-svc → SMC call → ATF / firmware → SDM → CRAM（fabric） │ svcbuffer@0 （bitstream 放在這裡）

所以錯誤訊息 firmware:svc:fpga-mgr 其實就是這個階層的字面展開： firmware 節點下的 svc 服務層裡的 fpga-mgr 客戶端。

4. 失敗過程逐步拆解

1驅動程式讀檔。 of_fpga_region 從 /lib/firmware 讀入 new40kHz4.core.rbf（1,351,680 bytes）。

2需要一塊 SDM 讀得到的緩衝區， 於是從專用保留區配置：

OF: reserved mem: 0x0000000080000000..0x0000000081ffffff (32768 KiB) nomap non-reusable svcbuffer@0

32 MB，專門切出來讓 firmware 讀取。nomap 表示不納入 kernel 線性映射， 因為擁有這塊記憶體定址權的是「不參與 Linux 記憶體管理的外部代理人」。

3dma_alloc_coherent() 回傳兩個不同的東西：

CPU 指標（VA）  →  用來 memcpy 把 bitstream 複製進去
dma_addr_t      →  要交給「裝置」的那個數字

4分歧就發生在這裡。 因為 svc 有 iommus 屬性，SMMU 配置了一個 IOVA。以示意數值說明：

bitstream 實際位於   0x8000_0000   ← 資料真正所在
dma_addr_t 回傳值    0xFFFF_0000   ← IOVA；SMMU 會把它映射到 0x8000_0000

兩個數字都「正確」— 只是對負責轉譯的那一方而言才正確。

5驅動程式送出 mailbox 命令給 SDM： 「bitstream 在 0xFFFF_0000，長度 N。」

6SDM 的路徑上沒有 SMMU。 它不會查任何分頁表，也沒有任何映射為它而設。 它把 0xFFFF_0000 當作字面上的實體位址去讀 DRAM。

SDM 讀取的位置 資料真正的位置 0xFFFF_0000（不相干的 DRAM） 0x8000_0000（bitstream） ▲ ▲ └──────────── 不一致 ────────────┘

7它找不到有效的 bitstream。 沒有 section header、沒有 magic、沒有任何它認得的組態資料。 因此它不會開始寫入 CRAM，而且關鍵是 — 它永遠不會回傳「緩衝區處理完畢」的回應。

8驅動程式就卡在等那個回應：

fpga_manager fpga0: writing new40kHz4.core.rbf to Stratix10 SOC FPGA Manager
Stratix10 SoC FPGA manager firmware:svc:fpga-mgr: timeout waiting for svc layer buffers

9實際觀察到的後果：

  • state 卡在 write — FPGA manager 從未離開寫入階段
  • 寫入行程進入 D state（不可中斷睡眠）， Ctrl-C 與 kill -9 都無效
  • systemd-journald 也一起卡住並觸發 watchdog 失敗
  • 需要重開機（甚至 power cycle）才能清除

結論：CRAM 從未被寫入，fabric 維持原本的組態不變。

5. 幾個容易誤解的重點

① 資料一直都在正確的位置。
這是這個 bug 反直覺的地方：memcpy 進 svcbuffer@0 是成功的， 保留區的實體位置正是 firmware 預期的位置，32 MB 容納 1.35 MB 的檔案綽綽有餘。 錯的只有 mailbox 訊息裡的那個數字。 因此「把緩衝區搬到別的位址」沒有用 — 兩端會一起搬過去，不一致依然存在。
② 逾時（timeout）而非錯誤（fault），正是診斷指紋。
如果是超出範圍或未映射的存取，會產生 SMMU fault 或回傳錯誤碼。 但讀到合法但錯誤的 DRAM 兩者都不會發生： SDM 看到垃圾資料，判斷沒事可做，然後就安靜了。 「沉默」正是位址轉譯不一致的特徵，而不是權限或範圍問題。
③ nomap 是結構性的矛盾。
這個旗標存在的原因，就是因為有個非 CPU 的代理人以實體位址存取這塊區域。 把這樣的區域放在一個會轉譯的 SMMU 後面，在設計上就是自相矛盾 — 所以修正方式必須是「讓那一個裝置不要被轉譯」，而不是去調整位址。
④ 這也解釋了為什麼 Terasic 自己的 ada.rbf 一樣失敗。
上述流程完全不依賴 bitstream 的內容、大小，或 HPS-First / FPGA-First 設定。 失敗發生在任何一個位元的組態資料被消耗之前。 這證明問題與我們的設計無關，而是板子出廠映像檔的問題。
⑤ altr,smmu_enable_quirk 的存在是強力線索。
device tree 的 svc 節點上同時有 iommus 與 altr,smmu_enable_quirk。後者的存在說明 Altera 知道 svc 與 SMMU 的組合需要特別處理 — 而逾時說明在這個 kernel build 上， 負責讀取這個 quirk 的機制並沒有生效。

6. 為什麼「換一個 SDM 能存取的位址」行不通

DMA API 不允許驅動程式說「請給我一個數值上等於實體位址的 IOVA」。 IOVA 是由 SMMU 自己的配置器從它的位址空間分配的，驅動程式只能被動接受。 沒有任何旋鈕可以要求「請 identity 映射這一塊」。

真正能讓 IOVA == PA 的機制就是 identity / passthrough domain — 也就是我們實測過的 iommu.passthrough=1（全域生效，但弄壞了 SD 卡）， 或是把 svc 節點的 iommus 移除（只對這一個裝置生效）。

7. 已排除的做法（實測結果）

測試 參數生效？ 板子開機？ RBF 載入？
iommu.passthrough=1 是
Default domain type: Passthrough		 失敗
mmc0: error -5		 無法測試
arm-smmu-v3.disable_bypass=0 是
但 domain 仍為 Translated		 正常 相同逾時
為什麼這兩個都不行：
  • iommu.passthrough=1 讓所有裝置 IOVA == PA。 svc 因此可以運作，但 sdhci-cdns 原本依賴 IOMMU 配置的位址窗， 改為 identity 映射後它的 descriptor 無法表達那些位址 — 於是出現 DMA 0x0000000000000000, LEN 0x0000 與 mmc0: error -5 whilst initialising SD card，root filesystem 掛不起來。
  • arm-smmu-v3.disable_bypass=0 只影響 沒有 device tree IOMMU 對應的 stream ID。 stratix10-svc 有明確的 iommus 屬性， 所以無論如何都會拿到會轉譯的 domain。

這兩個測試剛好從兩側夾出了問題本質： 全域 passthrough 修好 svc 卻弄壞 SDHCI；保留轉譯讓 SDHCI 正常但 svc 仍失敗。 沒有任何一個 kernel 命令列參數能同時滿足兩者 — 因此修正必須是針對單一裝置的，也就是改 device tree。

8. 可行的修正方向

修正方式 改變了什麼 代價
移除 svc 節點的 iommus 該裝置不再有 SMMU 對應，走 dma-direct， 因此 dma_addr_t == PA 需重建 DTB；只影響這一個裝置，其他裝置保有 IOMMU 防護
修改 stratix10-svc 驅動，改傳實體位址 驅動在 SMC 呼叫前自行轉換 需改 kernel 原始碼；但這在上游語意上更正確
更新板子的出廠映像檔 / 洽詢 Terasic 可能上游已修正 風險最低；但需等待
為什麼「驅動端修正」在上游語意上更正確： SDM 在 Linux 的意義下根本不是一個 DMA master — 它沒有被登錄進 SMMU，因此不存在任何對它而言正確的 dma_addr_t。 驅動程式應該明確傳遞實體位址，而不是把 DMA 層產出的數字直接送出去。 移除 iommus 只是用「讓兩者恰好相等」的方式達到同樣結果。
尚待確認： 若平台宣告了 dma-ranges 位移，即使沒有 IOMMU， dma_addr_t 仍會與 PA 相差一個 offset， 單純移除 iommus 就不足以解決。 動手之前應先檢查 /firmware/svc 上層匯流排是否有 dma-ranges。

建議的安全測試方式

利用 U-Boot 依檔名載入 DTB 的特性，可做到完全不破壞原檔的測試：

  1. 從板子取出 socfpga_agilex5_de25s.dtb，用 dtc 反編譯
  2. 只移除 svc 節點的 iommus，其餘節點完全不動
  3. 編譯成新檔名 socfpga_agilex5_de25s_nosmmu.dtb， 與原檔並存於 /boot
  4. 在 U-Boot 提示號下 fatload 新檔名，單次開機
  5. 測試 core.rbf 載入

原始 DTB 從未被修改，因此單純 power cycle 就會回到出廠設定。

9. 附註：這一切不影響 mailbox 的存取

Linux 存取 fabric_avalon_uart 的路徑是：

CPU → LWH2F bridge → Avalon slave @ 0x2000_0000 ← MMIO，CPU 主動發起

這是以 CPU 為發起端，所以走 MMU 而非 SMMU。因此：

  • mailbox 完全不需要 iommus 屬性 — 它不做 bus-master，只被動回應
  • 移除 svc 節點的 iommus 不可能影響驅動讀寫 DATA/STATUS/CONTROL
  • overlay 裡的 reg = <0x0 0x20000000 0x0 0x10> 是給 ioremap 用的實體位址，與 SMMU 無關
這一點乾淨地把兩個問題分開了： SMMU 的 bug 只侷限於 bitstream 的「載入」階段（svc → SDM，裝置主動發起）。 一旦 fabric 完成組態，與 mailbox 通訊純粹是 MMIO，完全不受影響。 所以修其中一個不會弄壞另一個。
