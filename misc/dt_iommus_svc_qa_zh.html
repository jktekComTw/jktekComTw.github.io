Device Tree 的 iommus、svc 與 method = "smc"

圍繞 iommus = <0x09 0x0a> 展開的八個問題 — phandle 機制、位址空間、SMC conduit、 altr,smmu_enable_quirk，以及為什麼「只移除 svc 的 iommus」在 Agilex 5 上行不通

DE25-Standard Agilex 5 (A5ED013BB32AE4SCS) Linux 6.12.11 arm-smmu-v3 stratix10-svc SMCCC / SiP

0. 這份文件的範圍

這是 smmu_rbf_load_failure_zh.html 的姊妹篇。 前一份說明「為什麼 RBF 載入會失敗」； 這一份逐項拆解在讀那份分析時自然會冒出來的基礎機制問題 — device tree 的數字到底代表什麼、誰替誰做位址轉換、 以及最後那個實際動手的問題：能不能只針對 svc 一個節點下手。

八個問題的一句話答案：
  1. 0x09 是 phandle（指向節點的指標），不是位址
  2. 16000000 是實體位址（PA / bus address），DT 裡永遠不會有 VA
  3. IOMMU 不是幫 CPU 轉址 — 它替裝置把 IOVA 轉成 PA
  4. svc 兩者都是：DT 節點名 + 綁上去的 stratix10-svc 驅動
  5. method = "smc" 選擇呼叫韌體的指令（SMC→EL3，HVC→EL2）
  6. altr,smmu_enable_quirk 是 Agilex 5 上的必要屬性 — SMMU 支援是刻意設計的，不是意外
  7. 不可以只移除 svc 的 iommus — Agilex 5 上會讓 svc probe 直接 -ENODEV 失敗
  8. 真正該做的是對齊 kernel + DTB + ATF 的版本， 並確認 quirk 在兩個節點上都存在
訂正說明（第 6–8 節）。 本文最初的第 6、7 節建議「移除 svc 節點的 iommus」。 在查閱 /home/vivado/kernel/linux-socfpga-6.12 （tag QPDS25.3.1_REL_FCS_FIX，6.12.43）的實際原始碼後， 確認該做法在 Agilex 5 上行不通，且 StreamID 10 確實承載真實流量。 第 6–8 節已依原始碼重寫；第 1–5 節的機制說明不受影響。

1. iommus = <0x09 0x0a> 裡的 0x09 是什麼？

phandle 0x09 是 iommu@16000000（arm,smmu-v3, #iommu-cells = <1>）， 所以 iommus = <0x09 0x0a> 是 SMMU 上的 stream ID 10 — 那 0x09 為何存在？

0x09 不是位址，而是一個 phandle — 指向另一個 DT 節點的 32-bit 指標。

iommus 遵循 DT 標準的「phandle + specifier」格式：

iommus = <phandle specifier...> 0x09 0x0a ↑ 指向哪個 IOMMU ↑ 對那個 IOMMU 而言的參數
Cell 角色 含意
0x09 phandle iommu@16000000 節點上 phandle 屬性的值。 由 dtc 在編譯時自動配發（0x01、0x02… 依序給每個被引用到的節點）。 數值本身沒有任何意義，只在這一份 .dtb 內部有效。
0x0a specifier 寬度由目標節點的 #iommu-cells = <1> 決定 → 只吃一個 cell。 對 arm,smmu-v3 而言這一個 cell 就是 StreamID → 10。

原始 .dts 裡其實不長這樣

你看到的是反編譯後的結果。人寫的原始碼是 label reference：

/* 原始 .dts — 人寫的 */
iommus = <&smmu 10>;

/* dtc 編譯後，&smmu 被換成 smmu 節點的 phandle 數值 */
iommus = <0x09 0x0a>;

要驗證這條連結的另一端，直接找誰宣告了 phandle = <0x09>：

dtc -I dtb -O dts system.dtb | grep -n 'phandle = <0x09>'
同一套機制在 DT 裡到處都是。 clocks = <&clk 3>、interrupts-extended、dmas、gpios、 memory-region 全是「phandle + specifier」， specifier 寬度一律由目標節點的 #*-cells 宣告。 看懂一個就看懂全部。

2. iommu@16000000 的 16000000 是 VA 還是 PA？

16000000 is va or pa?

是 PA（更精確地說：父匯流排位址空間中的位址）。 Device tree 裡永遠不會出現虛擬位址。

@ 之後的部分叫做 unit address， 依 DT 規範必須等於該節點 reg 的第一個位址。 而 reg 是用父節點的位址空間表示的：

父匯流排的 ranges unit address 的意義
空的 ranges; 或 identity mapping
（HPS 週邊匯流排的常態）		 = CPU 實體位址。 所以 0x1600_0000 就是 SMMUv3 register window 在 HPS memory map 裡的 PA。
非 identity 的 ranges
（如 PCIe、部分橋接器）		 是child bus address，必須沿著父節點鏈一路往 root 翻譯才會得到 CPU PA。

那 VA 什麼時候才出現？

只在 driver probe 的那一刻，由 kernel 動態產生，而且與 0x16000000 完全無關：

DT: reg = <0x0 0x16000000 ...> → devm_platform_ioremap_resource() → 回傳一個 kernel VA （固定寫在檔案裡的 PA） （每次開機可能不同）
為什麼 DT 不可能放 VA： DT 是在 kernel 啟動前就存在的靜態描述檔（U-Boot 交給 kernel 的一塊資料）。 那個時間點根本還沒有 page table、沒有 ioremap、也沒有任何 VA 的概念。 DT 描述的是硬體接線，硬體只認得實體位址。

3. IOMMU 是幫 CPU 把位址轉成 bus address 嗎？

iommu translate the address for cpu to bus address?

不是，方向剛好相反，而且 CPU 完全不參與。 SMMU 位於裝置與記憶體之間，不是 CPU 與匯流排之間。

CPU 側： VA ──[ CPU MMU ]──▶ PA ──▶ interconnect ──▶ DRAM 或 MMIO 裝置側： IOVA ──[ SMMU ]──▶ PA ──▶ interconnect ──▶ DRAM
轉譯器 服務對象 轉譯方向 依據
MMU CPU VA → PA process / kernel page table（TTBR0/1_EL1）
SMMU 會發起 DMA 的裝置 IOVA → PA 依 StreamID 查 stream table，再走該裝置 domain 的 page table

裝置放上匯流排的那個位址就是 IOVA， 也就是 Linux DMA API 裡 dma_addr_t 所裝的數值。 CPU 的 load/store 從來不會經過 SMMU。 這正是為什麼節點上加了 iommus， 對「CPU 讀寫該週邊的 register」完全沒有影響。

真正做「CPU ↔ bus 位址」轉換的是這兩個，但都不是 IOMMU

屬性 方向 性質
ranges child bus → parent bus
（往 CPU 側翻譯 reg）		 靜態位移。純粹的位址算術，在 DT 解析階段由軟體完成， 沒有硬體 page table。
dma-ranges 裝置 → 記憶體 同樣靜態。描述 interconnect 固定套用的視窗／位移。 即使完全沒有 IOMMU，它也會讓 dma_addr_t ≠ PA。

三個位址空間 — 只有兩個有機會相等

發起者 它送出的位址 被誰轉譯
CPU（kernel / user） VA MMU → PA
Linux 裝置做 DMA IOVA（dma_addr_t） SMMU → PA
SDM（remapper 啟用時） 經 SDM remapper 的位址 SDM 自己的硬體 remapper
SDM（remapper 停用時） IOVA + 0x8000_0000 SMMU（StreamID 10）
關於 SDM 的重要修正： 在 Agilex 5 上，SDM 讀取 DRAM 的路徑確實掛在 SMMU 後面， 對應的就是 StreamID 10。 SDM 另外有一顆自己的硬體 remapper； 當 Linux 決定用 SMMU 時，驅動會發 SMC 把那顆 remapper 關掉， 改由 SMMU 負責轉譯。詳見第 6 節。
因此「SDM 完全不在 SMMU 後面、只認 PA」並不適用於 Agilex 5。 這一點推翻了「移除 iommus 就能讓兩者相等」的想法 — 見第 7 節的 -ENODEV 分析。

4. svc 是一個 node 還是一個 kernel module？

svc is a node or kernel module?

兩者都是 — 而且是同一條繫結（binding）的兩端。 svc 這個名字是 DT 節點；stratix10-svc 是綁上去的驅動。

DT 節點

firmware {
    svc {
        compatible    = "intel,agilex5-svc";
        method        = "smc";
        memory-region = <&svcbuffer>;      /* svcbuffer@0，保留的 32 MiB */
        iommus        = <&smmu 10>;         /* ← 造成載入失敗的那一行 */

        fpga_mgr: fpga-mgr {
            compatible = "intel,agilex5-soc-fpga-mgr";
        };
    };
};

兩個關鍵觀察：

  • 它掛在 /firmware 底下，不是 /soc
  • 它沒有 reg — 因為它不是 MMIO 週邊。 它代表的是一條通往韌體的通訊管道，所以才有 method = "smc"。

驅動

drivers/firmware/stratix10-svc.c， config 為 CONFIG_INTEL_STRATIX10_SERVICE（tristate，因此可以是 stratix10-svc.ko，但 Altera 的預設 config 通常是 built-in）。 它註冊成 platform driver 來 match 上面那個 compatible。

它提供的是一個 service layer — 給其他驅動呼叫的 in-kernel API：

stratix10_svc_request_channel_byname(client, "fpga");
stratix10_svc_allocate_memory();   /* 從 svcbuffer@0 切一塊 */
stratix10_svc_send();              /* → SMC → ATF → SDM */

它的 consumer 是 drivers/fpga/stratix10-soc.c（FPGA manager）與 stratix10-rsu.c。

所以 log 為什麼寫 firmware:svc:fpga-mgr

因為帶有 compatible 的 DT 節點會被實例化成 platform device， 而 device 名稱就是把 DT 路徑的 / 換成 :：

DT 路徑 Linux device 名稱 驅動
/firmware/svc firmware:svc stratix10-svc
/firmware/svc/fpga-mgr firmware:svc:fpga-mgr stratix10-soc（FPGA mgr）
Stratix10 SoC FPGA manager firmware:svc:fpga-mgr: timeout waiting for svc layer buffers ↑ 子節點（fpga-mgr）抱怨父節點（service layer）沒交出可用的 buffer
最關鍵的一點：firmware:svc 是一個有 DT 節點的真實 struct device， 這正是 iommus 會生效、以及你會看到 stratix10-svc firmware:svc: Adding to iommu group 3 的原因。 一個純粹的 kernel module、沒有 DT 節點的話，永遠不會拿到 SMMU StreamID。

在板子上驗證

ls /proc/device-tree/firmware/svc/
ls -l /sys/bus/platform/devices/firmware:svc/driver
grep -i stratix10 /proc/modules      # 若是 built-in 則為空

5. method = "smc" 是什麼意思？

what does method = "smc" mean?

它選擇 conduit — 驅動用哪一條 ARM 指令呼叫韌體。 與 PSCI 的 method 是同一個屬性、同樣只有兩種合法值。

值 指令 trap 到 由誰處理
"smc" SMC #0 EL3 Secure Monitor — TF-A / ATF BL31
"hvc" HVC #0 EL2 Hypervisor

你的板子上 Linux 跑在 EL1 並且直接擁有 EL3 呼叫權，所以是 "smc"。 只有當 Linux 是 guest、且 EL2 的 hypervisor 要代為攔截／轉送韌體呼叫時，才會改用 "hvc"。

驅動拿這個字串做什麼

stratix10-svc.c 只是用它挑一個 function pointer：

if (!strcmp(method, "smc"))
        sh->invoke_fn = svc_smccc_smc;   /* → arm_smccc_1_1_smc() */
else if (!strcmp(method, "hvc"))
        sh->invoke_fn = svc_smccc_hvc;   /* → arm_smccc_1_1_hvc() */
else
        return -EINVAL;

之後每一次請求都走 sh->invoke_fn(...)。 這個字串是兩條路徑唯一的差別 — 參數的排列方式完全相同。

呼叫本身（SMCCC）

參數放在 x0–x7，其中 x0 是 function ID； 回傳值放在 x0–x3。 Altera 使用 SiP（Silicon Provider）廠商保留範圍： 

INTEL_SIP_SMC_FPGA_CONFIG_START            0xC2000001
INTEL_SIP_SMC_FPGA_CONFIG_WRITE           0xC2000002
INTEL_SIP_SMC_FPGA_CONFIG_COMPLETED_WRITE
INTEL_SIP_SMC_FPGA_CONFIG_ISDONE

0xC2… 解碼為：fast call / SMC64 / owner = SiP。

fpga-mgr → stratix10-svc → SMC #0 → EL3 TF-A → SDM mailbox → SDM → CRAM（fabric）

所以 svc 是一個門鈴（doorbell），不是週邊 — 這也解釋了為什麼它有 method 與 memory-region，卻沒有 reg。

這一點如何連回那個 bug

Bitstream 遠遠塞不進八個 register，所以 FPGA_CONFIG_WRITE 在 x1／x2 裡傳的是一個位址與一個長度，指向 svcbuffer@0。 EL3 的 TF-A 與 SDM 都把那個數值當成裸的實體位址解參考 — 兩者皆不在 SMMU 後面，也都不會去查 Linux 的 IOMMU page table。

但因為 /firmware/svc 帶著 iommus = <&smmu 10>， DMA API 交給驅動的是 IOVA。 於是：memcpy 進 buffer 成功（CPU 路徑，只經過 MMU）、SMC 也正常送達， 然後 SDM 去讀一個與 bitstream 實際位置毫無關係的實體位址 → timeout waiting for svc layer buffers。

Conduit 本身運作完美；出錯的是穿過它的那個「位址」屬於錯誤的位址空間。

6. altr,smmu_enable_quirk 是什麼？

altr,smmu_enable_quirk <-- ?

Altera 自訂的 boolean（有無即代表真假） DT 屬性。 它告訴驅動「這個平台的 SMMU 是啟用的，請走 SMMU-aware 的位址路徑」。 在 Agilex 5 上它不是可選的 — 缺了它 svc 根本不會 probe 成功。

兩份 binding 文件都有記載，內容一字不差：

Documentation/devicetree/bindings/firmware/intel,stratix10-svc.txt:42
Documentation/devicetree/bindings/fpga/intel-stratix10-soc-fpga-mgr.txt:14

  - altr,smmu_enable_quirk: set when SMMU is enabled for the platform.

而在 arch/arm64/boot/dts/intel/socfpga_agilex5.dtsi 裡， 它同時出現在兩個節點上（第 226 與第 230 行）： 

svc {
    compatible = "intel,agilex5-svc";
    iommus     = <&smmu 10>;
    altr,smmu_enable_quirk;                     /* :226 */

    fpga_mgr: fpga-mgr {
        compatible = "intel,agilex5-soc-fpga-mgr";
        altr,smmu_enable_quirk;                 /* :230 */
    };
};

svc 端：drivers/firmware/stratix10-svc.c:3607

if (of_device_is_compatible(node, "intel,agilex5-svc")) {
    if (iommu_present(&platform_bus_type) &&
        device_property_read_bool(dev, "altr,smmu_enable_quirk")) {

            controller->is_smmu_enabled     = true;
            controller->sdm_dma_addr_offset = AGILEX5_SDM_DMA_ADDR_OFFSET;  /* 0x8000_0000 */
            controller->domain = iommu_get_dma_domain(dev);
            if (!controller->domain) { ret = -ENODEV; goto err_destroy_pool; }

            iova_cache_get();
            iommu_attach_device(controller->domain, dev);
            init_iova_domain(&controller->carveout.domain, ..., IOMMU_STARTING_ADDR);  /* 0x0        */
            controller->carveout.limit = IOMMU_LIMIT_ADDR - PAGE_SIZE;                 /* 0x2000_0000 */

    } else {
            ret = -ENODEV; goto err_destroy_pool;   /* ← 沒有 non-SMMU 分支 */
    }

    /* SMMU 接手轉譯，所以把 SDM 自己那顆 remapper 關掉 */
    controller->invoke_fn(INTEL_SIP_SMC_SDM_REMAPPER_CONFIG,
                          is_smmu_enabled ? DISABLE_REMAPPER : ENABLE_REMAPPER, ...);
常數 值 用途
AGILEX5_SDM_DMA_ADDR_OFFSET 0x8000_0000 送給 SDM 前加在 IOVA 上的位移
IOMMU_STARTING_ADDR 0x0 svc 專屬 IOVA domain 的起點
IOMMU_LIMIT_ADDR 0x2000_0000 IOVA domain 上限（實際 limit 再減一個 PAGE_SIZE）
INTEL_SIP_SMC_FUNCID_SDM_REMAPPER_CONFIG 513 開關 SDM remapper 的 SMC function（需 ATF 支援）

fpga-mgr 端：drivers/fpga/stratix10-soc.c

同一個屬性在子節點上決定 bitstream buffer 要不要做 DMA mapping：

/* :459 */
priv->is_smmu_enabled = device_property_read_bool(dev, "altr,smmu_enable_quirk");

/* :302 — 每個 buffer 送出前 */
if (priv->is_smmu_enabled)
        priv->svc_bufs[i].dma_addr = dma_map_single(dev, svc_buf, SVC_BUF_SIZE, DMA_TO_DEVICE);

/* :139 — buffer 回收時 */
if (priv->is_smmu_enabled == true)
        dma_unmap_single(priv->client.dev, priv->svc_bufs[i].dma_addr, SVC_BUF_SIZE, DMA_TO_DEVICE);

然後在 svc 送出訊息時補上位移（stratix10-svc.c:3253）：

if (p_msg->command == COMMAND_RECONFIG_DATA_SUBMIT && chan->ctrl->is_smmu_enabled)
        p_data->paddr += chan->ctrl->sdm_dma_addr_offset;   /* IOVA + 0x8000_0000 → SDM */

結構體註解（:271）寫得很直白： "dma addr offset to append to the IOVA sent to SDM"。

結論：SMMU + svc 是「刻意設計」要能運作的組合，不是天生壞掉的搭配。 設計意圖是：Linux 用 SMMU 管 SDM 的 DRAM 存取（StreamID 10）， 把 SDM 自己的 remapper 關掉，並在傳址時補上 0x8000_0000 的固定位移。 這條路徑需要 kernel、DTB、ATF 三者版本一致才會成立。

7. 可以只移除 svc 的 iommus 嗎？

can i remove iommus only for svc? / remove iommus for svc would not affect other device?

在 Agilex 5 上不行。 intel,agilex5-svc 的 probe 路徑沒有 non-SMMU 分支， 移除後 svc 會直接 -ENODEV 失敗。

兩種移除方式都會失敗

你做的修改 程式碼走到哪裡 結果
只移除 iommus，保留 quirk iommu_present() 仍為真、quirk 仍為真 → 進入 SMMU 分支， 但 iommu_get_dma_domain(dev) 回傳 NULL -ENODEV
兩個都移除 條件不成立 → 走 else -ENODEV
svc probe 失敗的連帶損失： fpga-mgr、hwmon、fcs-config 都是 svc 的子節點， 父節點沒 probe 成功就不會被建立。 也就是整個 FPGA 重組態、RSU、溫度電壓監測、FCS 全部一起失效 — 代價遠大於原本那一個 bug。
那為什麼舊平台可以？ 整個 quirk 區塊被 of_device_is_compatible(node, "intel,agilex5-svc") 包住。 intel,stratix10-svc 與 intel,agilex-svc 根本不會進入這個分支，所以在那些 SoC 上移除 iommus 是可行的。 這個限制是 Agilex 5 專屬的。

順帶訂正：StreamID 10 有真實流量

本文早期版本推測「firmware:svc 沒有 reg、不 master 任何東西， 所以 SID 10 上大概沒有真實流量」。這是錯的。 INTEL_SIP_SMC_SDM_REMAPPER_CONFIG 的存在本身就證明了： SDM 有一條會被 remapper 或 SMMU 轉譯的 DRAM 存取路徑， 而那條路徑對應的就是 StreamID 10。 firmware:svc 是 Linux 端代為持有並設定這個 StreamID 的 proxy device。

「iommus 逐節點生效」這件事仍然成立

第 7 節結論改變的是「該不該對 svc 動手」， 而不是 iommus 的作用範圍。 of_iommu_configure() 依然只讀該節點自己的 iommus， 所以下列理解不變：

節點 若移除 svc 的 iommus 說明
sdhci-cdns / USB / EMAC 完全不受影響 各自保有 iommus、domain 與 STE
/firmware/svc probe 失敗 並非「安靜地退回 dma-direct」，而是驅動主動拒絕上線
所以 iommu.passthrough=1 會弄壞 sdhci-cdns 的原因依然如第 3 節所述 — 它翻轉的是全域的 default domain type。 「逐節點」的判斷正確；錯的是把 svc 當成可以安全下手的那個節點。

8. 那實際上該檢查什麼？

svc 在你的板子上是 probe 成功的（否則 fpga-mgr 不會存在、也就印不出那行 timeout），所以 SMMU 路徑本身已經起來了。 問題出在下游的 buffer／位址處理，而最可能的原因是版本不一致。

版本落差

項目 版本 來源
失效的執行環境 6.12.11 板子上的 uname -r
本地含完整 quirk 支援的樹 6.12.43 /home/vivado/kernel/linux-socfpga-6.12
tag QPDS25.3.1_REL_FCS_FIX、refdes 25.3.1

最可能的單一根因：quirk 只加在其中一個節點

quirk 在 svc 上、卻漏在 fpga-mgr 上時：
  • fpga-mgr 的 is_smmu_enabled 為 false → 不做 dma_map_single()
  • 但 svc 的 is_smmu_enabled 為 true → 仍然照樣 paddr += 0x8000_0000
  • 於是 SDM 拿到一個從未被映射過、又被加了位移的位址 → 永遠不回 buffer
  • 結果就是那行 timeout waiting for svc layer buffers

在板子上要跑的檢查

uname -r

# quirk 必須「兩個節點都有」
ls /proc/device-tree/firmware/svc/altr,smmu_enable_quirk
ls /proc/device-tree/firmware/svc/fpga-mgr/altr,smmu_enable_quirk

# remapper 交握是否成功
dmesg | grep -i 'remapper\|Service Layer'
怎麼讀這些輸出：
  • Failed to configure remapper! 是 pr_info， 一定會出現在 dmesg。你的 log 裡沒有它 → 代表 ATF 確實實作了 funcid 513，remapper 交握成功。
  • IOMMU Present / IOMMU Not Present 是 pr_debug， 需要 dynamic debug 才看得到 — 看不到不代表沒發生。
  • 兩個 ls 都要成功。只有一個成功就是根因。

建議的修正順序

順序 動作 理由
1 確認執行中的 DTB 兩個節點都有 quirk 零風險，且可能直接就是答案
2 把 kernel、DTB、ATF 全部對齊到同一個 release （本機這棵 25.3.1 樹） IOVA 視窗、0x8000_0000 位移、funcid 513 三者是同一份協定，混版就會失效
3 仍失敗才考慮改驅動 在確認協定版本一致之前改驅動，只會掩蓋真正的不一致
不要再走的兩條路： iommu.passthrough=1（全域，會弄壞 sdhci-cdns） 與移除 svc 的 iommus（Agilex 5 上會讓 svc 完全不上線）。 兩者都不是這個平台的正解。
